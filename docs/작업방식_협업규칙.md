# 작업 방식과 협업 규칙 합의문 (Git · 병합 요청 · 검토)

저장소: https://github.com/no-people/py_KKMOYS

함께 보는 문서: [역할분담_작업순서.md](역할분담_작업순서.md) · [공통모듈_함수규격.md](공통모듈_함수규격.md) · [규약.md](규약.md)

- 이 문서는 팀원 6명(김보근, 강동휘, 민기슬, 손가인, 염승민, 오재원)이 합의한 작업 규칙이다. 합의한 사람은 이 문서 병합 요청의 승인·의견으로 확인한다.
- 이 문서를 바꿀 때도 병합 요청과 검토를 거친다.

## 1. main 규칙

- main 에는 직접 push 할 수 없다. 모든 변경은 브랜치를 만들어 병합 요청(PR)으로 넣는다.
- 병합하려면 두 가지가 모두 필요하다.
  - 다른 팀원 1명 이상의 승인(Approve). 자기 PR은 자기가 승인할 수 없다.
  - 자동 검사 `check` 통과(문법 검사, 기능끼리 import 검사, 팀 테스트).
- 강제 push(force push)와 main 삭제는 막혀 있다.
- 관리자를 포함해 누구도 이 규칙을 건너뛸 수 없다. 규칙은 끄거나 바꾸지 않는다.
- 병합 방식은 "Create a merge commit" 하나만 쓴다(스쿼시·리베이스 병합은 꺼져 있다).
- 관리자: Jxnznx(팀장 손가인), dajugeum07(김보근).

### 병합 요청 하나에 담는 것

- **한 가지 변경만** 담는다(기능 하나, 수정 하나, 공통 함수 하나).
- 변경은 **300줄 이하**로 한다. 넘으면 나눠서 올린다.
- 기능이나 공통 함수를 넣으면 그 **테스트도 같은 병합 요청에** 넣는다.
- `moim/common` 을 바꾸면 무엇을 왜 바꿨는지, 어느 기능이 쓰는지 설명에 적는다(규약.md 8절).
- 병합은 승인을 받은 뒤 **작성자 본인**이 한다.

## 3. 작업 순서

1. 최신 main 받기
   ```
   git checkout main
   git pull
   ```
2. 브랜치 만들기. 이름은 `종류/범위-내용`이고, 범위는 4절 표의 이름을 쓴다 (예: `feat/settle-report`, `fix/common-split-remainder`, `docs/readme-usage`)
   ```
   git checkout -b feat/settle-report
   ```
3. 작업한 뒤 올리기 전에 직접 검사하기
   ```
   python -m compileall -q moim tools
   python tools/check_imports.py
   python -m unittest discover -s tests
   ```
4. 커밋하고 브랜치 올리기
   ```
   git add 바꾼파일
   git commit -m "feat(settle): 정산 보고서 출력 추가"
   git push -u origin feat/settle-report
   ```
5. GitHub에서 병합 요청 만들기. push 결과에 나오는 링크를 열고 **Create pull request**를 누른다. 설명은 **5절 양식**대로 쓴다.
6. **6절 표의 검토자**를 Reviewers에 지정한다. 승인하는 사람은 **Files changed → Review changes → Approve → Submit review**를 누르고, 의견은 **7절 방식**으로 쓴다.
7. `check` 가 초록색이고 승인이 있으면 **Merge pull request → Confirm merge**를 누른다.
8. 병합한 뒤 정리
   ```
   git checkout main
   git pull
   git branch -d feat/settle-report
   ```

## 4. 커밋 메시지

- `종류(범위): 한 줄 요약` 형식으로 쓴다.
- 종류: `feat`(기능 추가) · `fix`(오류 수정) · `test`(테스트) · `docs`(문서) · `refactor`(동작 그대로 구조 정리) · `chore`(설정·도구) · `revert`(되돌리기)
- 범위: 아래 표의 이름 중 하나를 쓴다. 브랜치 이름의 `범위` 자리에도 같은 이름을 쓴다.
- (예: `feat(expense): 지출 추가 시 0원 이하 금액 거부`, `fix(budget): 탈퇴일 다음 날 은행 출금에서 탈퇴자 제외`, `docs(readme): 정산 명령 사용 예와 출력 예 추가`, `test(settle): 100원을 세 명이 나눌 때 나머지 1원 경계값 테스트`)

| 기능·작업 | 범위 이름 |
|---|---|
| 1. 지출 입력·관리 | `expense` |
| 2. 분류 규칙 | `category` |
| 3. 보고서 | `report` |
| 4. 정산 | `settle` |
| 5. 예산·회비 | `budget` |
| 6. 가져오기·내보내기 | `io` |
| 공통 모듈 | `common` |
| 통합 실행 | `cli` |
| 설정 파일 | `config` |
| 로그 | `log` |
| 손상 대응 | `backup` |
| 사용 설명서 | `readme` |
| 통합 시나리오 | `scenario` |

- `moim/common` 의 함수를 채우는 커밋은 기능 범위가 아니라 `common` 을 쓴다.
- 한 커밋에는 한 범위만 담는다. 두 범위를 함께 바꿔야 하면 커밋을 나눈다.

## 5. 병합 요청에 적을 내용

병합 요청 설명에 아래 양식을 붙여 채운다. 빈칸이 있으면 검토자는 승인하지 않는다.

```markdown
## 변경 내용
- (무엇을 바꿨는지, 함수 이름 단위로)

## 변경 이유
- (어느 요구사항 때문인지. 예: 기능 1 기본 필수 "입력 검증")

## 확인 방법
- 실행한 명령: `python -m unittest discover -s tests`
- 결과: (예: Ran 27 tests, OK (skipped=20))
- 직접 실행 예: `python -m moim exp add ...` → (출력)

## 공통 모듈 변경 (해당할 때만)
- 바꾼 함수·자료 항목:
- 이 함수를 쓰는 기능:
- 맞춘 규약 값과 공통모듈_함수규격.md 의 절:

## 검토자
- 주 검토자: (이름) / 보조 검토자: (이름)
```

## 6. 검토자 배정 방식

각자 주 검토자 한 자리와 보조 검토자 한 자리를 맡아 부담을 똑같이 나눈다.

| 작성자 | 주 검토자 | 보조 검토자 |
|---|---|---|
| 김보근 (기능 1) | 손가인 | 염승민 |
| 강동휘 (기능 2) | 민기슬 | 손가인 |
| 민기슬 (기능 3) | 강동휘 | 오재원 |
| 손가인 (기능 4) | 김보근 | 강동휘 |
| 염승민 (기능 5) | 오재원 | 김보근 |
| 오재원 (기능 6) | 염승민 | 민기슬 |

- 주 검토자는 반드시 검토한다. 보조 검토자는 7-3 의 **넘기는 시점(12시간)** 이 지나도 주 검토자가 답하지 않으면 대신 검토한다. 보조 검토자도 답이 없으면 팀장이 맡는다.
- **공통 모듈 병합 요청**은 그 함수를 쓰는 기능의 담당자도 검토자로 지정한다(공통모듈_함수규격.md 의 "공용" 기능). 예: `queries.period_total`(오재원) → 민기슬·염승민.
- **팀 공동 작업 병합 요청**은 그 작업과 맞춰야 하는 담당자를 검토자로 지정한다(역할분담_작업순서.md). 예: 로그(김보근) → 통합 실행 손가인.
- 1인당 다른 사람의 병합 요청을 **5건 이상** 검토하고 의견을 남긴다. 팀장은 매주 월요일과 목요일에 사람별 검토 건수를 세어, 모자란 사람에게 검토를 더 배정한다.

## 7. 검토할 때 확인할 항목과 응답 기한

### 7-1. 확인 항목

검토 의견에 항목마다 결과를 적는다.

- [ ] 자동 검사 `check` 통과
- [ ] 브랜치를 직접 받아 실행해 봄. 실행한 명령과 결과를 적는다
  ```
  git fetch origin
  git checkout 브랜치이름
  python -m unittest discover -s tests
  ```
- [ ] 규약.md 의 값과 대조함: 사사오입(`round()` 금지), 나머지 1원 순서, 기간 양 끝 포함, 탈퇴일 당일까지 회원, 확정 기간 잠금, "미분류"(`UNCATEGORIZED`), 삭제 표시 제외. 대조한 줄을 적는다
- [ ] 공통모듈_함수규격.md 의 받는 값·돌려주는 값과 같음
- [ ] 스켈레톤 코드의 함수 이름과 인자를 바꾸지 않음
- [ ] 기능 파일끼리 서로 import 하지 않음
- [ ] 한 병합 요청에 한 변경, 300줄 이하, 테스트 포함
- [ ] 다른 사람의 기능 파일이나 다른 사람의 변경을 지우거나 고치지 않음
- [ ] `store.py` 의 `EMPTY` 에는 항목을 하나만 추가함 (8절 순서)
- [ ] 비밀번호·토큰·`config.json`·`data.json` 같은 개인 자료 파일이 들어 있지 않음

### 7-2. 검토 의견 쓰는 법

"확인했습니다"만 적은 검토는 검토 건수에 들어가지 않는다. 아래처럼 적는다.

```
- 실행: python -m unittest discover -s tests → Ran 27, OK (skipped=18)
- 규약 대조: queries.py 41행 expenses_in 이 dates.in_period 를 써서 끝일(11-30)을 포함함
- 규격 대조: 공통모듈_함수규격.md 3-1 과 같이 날짜순·같은 날 번호순으로 돌려줌
- 의견: include_deleted=True 일 때 삭제 표시 지출이 나오는 테스트를 하나 추가해 주세요
- 결론: 수정 요청 / 승인
```

### 7-3. 응답 기한

- 검토 요청을 받으면 **2시간 안에** 승인하거나 수정을 요청한다.
- **12시간** 안에 답이 없으면 작성자가 보조 검토자에게 넘기고 팀 대화방에 알린다. 보조 검토자도 2시간 안에 답이 없으면 팀장(손가인)이 검토하거나 다른 팀원에게 배정한다.
- **밤 12시부터 아침 9시까지(00:00~09:00)는 시간 계산에서 뺀다.**
  - 예: 23:00 에 요청 → 23:00~24:00 1시간 + 09:00~10:00 1시간 → 응답 기한은 **다음 날 10:00**.
  - 예: 15:00 에 요청 → 15:00~24:00 9시간 + 09:00~12:00 3시간 → 보조 검토자에게 넘기는 시점은 **다음 날 12:00**.
- 마감은 **병합된 시각**으로 판정한다. 승인을 받을 시간을 두고, 팀 내부 병합 마감은 공식 마감 하루 전 23:59로 한다(기본 필수 11/23, 최종 11/30). 공식 마감 시각(11/24·12/1 23:59)은 위의 제외 시간과 상관없이 그대로다.

## 8. 같은 파일을 여러 명이 고쳐 충돌이 났을 때

### 8-1. 처리 순서

1. 내 브랜치에서 최신 main 을 받아 합친다.
   ```
   git checkout 내브랜치
   git pull origin main
   ```
2. 충돌 난 파일에서 `<<<<<<<`, `=======`, `>>>>>>>` 사이의 **두 변경을 모두 살린다.** 다른 사람의 변경은 지우지 않는다.
3. 어느 쪽을 살려야 할지 모르면 **그 변경을 쓴 사람에게 묻는다**(`git log -p 파일` 또는 `git blame 파일`로 누가 썼는지 확인). 답을 받기 전에는 병합하지 않는다.
4. 다시 검사한다.
   ```
   python -m compileall -q moim tools
   python tools/check_imports.py
   python -m unittest discover -s tests
   ```
5. 커밋하고 올린다.
   ```
   git add 수정한파일
   git commit
   git push
   ```
6. 병합 요청에 "충돌 해결: (파일) — (누구의 어떤 변경) 모두 유지"라고 의견을 남긴다.

### 8-2. 충돌이 잦은 파일

- **`moim/common/store.py` 의 `EMPTY`**: 한 병합 요청에 항목 하나만 추가한다. 아래 순서를 지키고, 앞 순서가 병합된 뒤에 main 을 받아 올린다.
  1. `history`, 지출의 `deleted` (김보근)
  2. `locks` (손가인)
  3. `payments` (염승민)
  4. 지출의 `weights` (손가인)
  5. `transfers` (손가인)
  6. `recurring`, 지출의 `recurring_id` (손가인)
  7. 지출의 `category_fixed` (강동휘)
- **`moim/common/store.py` 의 `save`·`backups`·`recover`**: 민기슬(자료 파일 손상 대응)만 고친다. 다른 사람은 `EMPTY` 와 `record` 만 고친다.
- **`moim/common/queries.py`**: 자기 함수 본문만 고친다. 함수 순서를 바꾸거나 다른 사람의 함수를 손대지 않는다.
- **`moim/cli.py`**: 손가인(통합 실행)이 틀을 관리한다. 각 기능 담당은 자기 명령 묶음을 붙이는 줄만 더한다.

## 9. 자주 생기는 일

- **`push declined due to repository rule violations`**: main 에 직접 push 했다. 브랜치를 만들어 다시 올린다.
  ```
  git checkout -b fix/내용
  git push -u origin fix/내용
  ```
  그 뒤 main 을 원래대로 돌리려면 팀장에게 묻는다.
- **`check` 실패**: PR 화면의 `check` 옆 **Details** 에서 어느 단계가 실패했는지 보고, 고친 뒤 같은 브랜치에 다시 push 한다. PR에 자동으로 반영된다.
- **`Everything up-to-date`**: 올릴 새 커밋이 없다. `git add` 만 하고 `git commit` 을 안 했는지 확인한다.
- **남이 맡은 공통 함수가 급할 때**: 직접 고치지 말고 담당자에게 요청하거나 그 병합 요청에 의견을 단다. 함수 이름과 인자는 정해져 있으니 부르는 코드를 먼저 써 두고, 내 테스트에서는 `store.data["expenses"]` 에 dict 를 직접 넣는다.

## 10. 하지 않는 것과 되돌리기

- main 에서 바로 작업하지 않는다.
- 남의 브랜치에 말없이 push 하지 않는다.
- 다른 사람이 맡은 기능 파일을 그 담당자의 승인 없이 고치지 않는다.
- 승인 없이 병합하려고 규칙을 바꾸지 않는다.
- 비밀번호·토큰·개인 자료 파일(`config.json`, `data.json`, `backup/`, `logs/`)을 커밋하지 않는다.
- 규약.md 의 값은 교수의 승인 없이 바꾸지 않는다.
- 잘못 병합한 것은 기록을 지우지 않고 **`git revert`** 로 되돌리는 커밋을 새로 만들어 병합 요청으로 올린다.
  ```
  git checkout -b revert/범위-내용
  git revert -m 1 병합커밋번호
  git push -u origin revert/범위-내용
  ```
- 인수 테스트(11/25 공개)가 실패하면 **고치기 전에** `git log -p`, `git blame`, `git bisect` 로 원인 커밋을 찾아 감사 보고서용으로 기록한 뒤 고친다.
